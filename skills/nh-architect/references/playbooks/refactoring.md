> Adapted for consumer applications from the public NeoHaskell project.

### Refactoring

**You own the contract. The structure changes. The behavior does not.** Distinct from Feature, which adds behavior, and Bug fix, which corrects it.

Application API, serialization, and generated-client changes must migrate their actual callers with the same change. Use the compatible API guide and the existing consumer checks; a framework starter or testbed checkout is not required.

If the cleanup reveals a missing feature or a real bug, split it out and ship the structural change first against the pinned contract. A redesign is allowed, but name it and route to Feature. Large or cross-cutting structural work belongs to the **nh-figure-it-out** skill. This playbook is the focused-to-medium change.

1. Pin the behavior contract first. Run the **nh-how** skill over the affected subsystem to learn the contract, then write a characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves. If the area has no coverage, write the pin before touching structure. Use meaningful Hspec examples or QuickCheck properties with independently specified expectations or a genuinely preserved baseline. For public/generated compiler/API contracts, compile representative consumer fixtures, including rejected uses where relevant. Ordinary typecheck and lint alone do not pin runtime behavior; demand pure results and execute Tasks/service effects for runtime equivalence.
2. Name the structure the code is missing per **nh-principle-model-the-domain**. Boring code stays when the shape is already clear and local. The reshape must clarify contracts or ownership and reduce reader load; branch deletion alone is not the measure. Preserve useful framework boundaries rather than adding incidental indirection.
3. Name the target shape. State what the module layout, types, and call graph should be if built today (**nh-principle-foundational-thinking**, **nh-principle-redesign-from-first-principles**). For a meaningful shape, contract, module/service ownership, effect/concurrency or generation decision, run **nh-architect** for parallel design exploration only before the move. Follow [NeoHaskell best practices](../../../nh-best-practices/SKILL.md) and [code guidelines](../../../nh-code-guidelines/SKILL.md).
4. Subtract before you add. Establish redundancy before deleting code, collapsing wrappers or dropping validators: inspect exports, class/instance adapters, useful service facades, generated references and the guarantee each check establishes. Preserve required operation-specific checks and remove proven dead code or orphan references before introducing the new shape (**nh-principle-subtract-before-you-add**). The smallest change that reaches the target shape ships (**nh-principle-minimal-change**). A speculative cleanup that "might help" gets reverted.
5. Move in coherent behavior-preserving Haskell steps, each keeping the pin green: include the types, instances, generators and affected consumers required for that contract and preserve evaluation/effect semantics at each declared migration boundary. For internal API reshapes where no external compatibility obligation exists and coordinated breaking changes are feasible, migrate all callers and delete the old API in the same wave, without shims or parallel paths (**nh-principle-migrate-callers-then-delete-legacy-apis**). Public/generated consumer compatibility remains part of the contract unless an intentional breaking change is authorized; follow existing design and the consumer's release and compatibility policy. A local text search cannot establish the absence of external consumers. Spot-check every rename against the actual files. Inventory exports, generated name lookups, compiler fixtures, strings, documentation and back-references as well as direct calls. Delegate the mechanical edits through scoped implementer roles in `AGENTS.md`, within actual capacity, with a specific scope (file paths, the names being moved, the behavior to hold).
6. Prove behavior is unchanged on the real artifact, not "it compiles" (**nh-principle-prove-it-works**). For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface via the relevant control skill.
7. Confirm the change is worth keeping. The success measure is reduced reader load (**nh-principle-minimize-reader-load**). If the diff does not lower reader load somewhere, revert it.
8. Rebase into small ordered commits. A subtraction commit, then the reshape, then any follow-on cleanup. Shape them with the **sequence-verifiable-units** principle skill, so each behavior-preserving slice stays green before the next. Run **Opening a PR**.

**Reply:** the structure that changed, the pin you held it against, the equivalence proof, the reader-load delta, what shipped and what got reverted. No new behavior.
