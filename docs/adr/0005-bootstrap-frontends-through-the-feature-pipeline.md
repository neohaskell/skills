# Bootstrap missing frontends through the full-stack feature pipeline

The feature pipeline is the user-facing entry point for full-stack delivery by default. It invokes a new `nh-frontend-setup` skill when the consumer application lacks a frontend, then continues the requested feature through backend, client, frontend, and verification. This separates initial scaffolding from recurring feature development without requiring the user to invoke setup separately, and extends the approved catalog in [ADR 0002](0002-omakase-catalog-and-portable-resources.md) from 96 to 97 skills.

The initial bootstrap uses React, TypeScript, and Orval. The configured service URL supplies the OpenAPI contract. It defaults to the local NeoHaskell service; `http://localhost:8080/openapi.json` is an example, not a universal address. Nick subsequently allowed any user-selected URL, including test or production services, without environment selection or classification by the skill. This amends the original local-only authority. Existing application tooling and choices are preserved, and reruns reconcile configuration without replacing handwritten content. No maintained or committed OpenAPI copy is introduced; temporary generator input remains allowed.

Orval configuration and project scripts hold the setup facts. No additional API profile document or mandatory `api.md` is required: copying discoverable configuration would create a second source to maintain. This replaces the earlier proposed profile and expands the original API-only planning boundary to include the minimal missing-frontend bootstrap and full-stack pipeline routing.

Every frontend build runs Orval directly against the configured URL before compilation, including the initial compilation performed by the development command. Generated SDK files stay out of Git and are regenerated for that build. Generation or compilation failure stops the command visibly with a failing exit status; an unavailable service does not permit fallback to a previous SDK. This deliberately makes frontend compilation depend on the configured backend being reachable. There is no backend watcher or restart trigger, separate schema-fetch stage, backend revision/freshness validation, extra synchronization test machinery, or required generation receipt. The configured service is assumed to be the intended running backend; choosing an old process is the user's responsibility.

The pipeline coordinates the journey, `nh-app-context` discovers executable configuration, `nh-frontend-setup` reconciles missing frontend or generation tooling, `nh-api-client` owns client alignment, and `nh-frontend` completes the UI. An existing frontend without generation tooling reaches setup without being scaffolded again. The existing collection installer distributes the new skill; application configuration happens through the pipeline when needed. Collection installation and application setup remain separate operations, preserving application-owned customizations.

For an application feature touching UI, delivery requires relevant application checks and observing the real UI-to-API path through the requested result. Compilation alone establishes compilation; unavailable access leaves runtime verification explicitly incomplete. For this skill-library change, delivery uses focused checks of metadata, relative links, routing, the 97-entry catalog, and the agreed build/development failure behavior, plus checks of any added executable helpers. This does not require a demo consumer, evaluation campaign, or certification and does not reinstate synchronization machinery excluded above.
